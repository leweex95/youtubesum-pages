PROJECT WALKTHROUGH

A small web form.
A private processing workflow.

This is a personal tool, not a public summarization service. The website accepts an owner-only request; a separate private system processes it and emails the result.

01

From link to email

Each part has one job and a clear boundary.

  1. 01

    Owner signs in and configures a request

    The page accepts one public YouTube video URL, a summarization approach, and selected summary formats. Prompt edits apply to that request only.

  2. 02

    A server checks and tracks the request

    A Cloudflare Worker verifies the GitHub account, validates the settings, and dispatches the private workflow. While it is queued or running, the page can request cancellation; GitHub confirms when the run has stopped. The page receives coarse progress milestones, not workflow logs or content.

  3. 03

    The Windows runner reads captions

    The runner uses yt-dlp for video details and available subtitles; it does not download the video. It preserves the original captions and creates a separate cleaned transcript.

  4. 04

    The app prepares and summarizes text

    Long transcripts are split into sections and combined into a final summary. TextGenHub sends summary requests through the owner’s signed-in ChatGPT browser session. This depends on that session and on ChatGPT’s current website.

  5. 05

    Optional audio, then email

    VoiceGenHub creates the requested narration and FFmpeg encodes an MP3. If narration fails, the app skips email rather than sending an incomplete result. Finished files are emailed through configured SMTP.

02

Where data goes

The public page is not where the video is processed.

Public website

Hosts the form and sign-in flow. The browser sends the link directly to the Worker; the Pages host does not receive it. The public site does not display transcripts, summaries, or job logs.

Private runner

Runs the Python app and keeps transcripts, summaries, audio, and checkpoints in its configured workspace. Subtitle text is sent to ChatGPT for summarization.

Other services

YouTube supplies captions. The optional narration provider receives the selected summary text. SMTP delivers the finished files to the configured inbox.

03

Engineering choices

These choices make the workflow easier to check, recover, and change.

Narrow request boundary

The bridge accepts one validated video URL and can trigger or cancel only the intended private workflow. A request-scoped cancellation token cannot control another run. It does not return private output to the browser.

Keep work resumable

Successful processing stages are checkpointed. On a retry, the app checks that inputs, settings, and saved files still match before reusing results.

Make services replaceable

YouTube, text generation, narration, and email are separated behind small interfaces. Most tests use fakes, not live accounts or paid services.

Separate AI from control logic

AI writes the summaries. Link validation, file handling, checkpoints, retries, and email rules are regular code with explicit tests.

Report partial failures honestly

A summary can be kept if an optional step fails. The job reports warnings and does not label missing narration as a complete emailed result.

Treat captions as input, not instructions

Video captions can contain misleading text. Prompts ask ChatGPT to summarize them, not to follow directions found inside the transcript.

04

Limits

Important dependencies are stated plainly.

  • The Windows PC and its self-hosted runner must be online. GitHub’s queue is temporary; this is not a durable job service.
  • Captions may be missing or inaccurate. ChatGPT browser automation can break when login, usage limits, or the website changes.
  • Email and narration depend on configured services. If the runner is offline or a provider fails, the request may not finish.
  • The request form stays disabled until the complete sign-in-to-email flow has been verified.
